### 2.2 工程：从空目录到可运行

**环境**：仓颉工具链 `Cangjie Compiler 1.0.5 (cjnative)`，Target `x86_64-w64-mingw32`，SDK 位于 `C:\Program Files (x86)\Cangjie`（MinGW + LLVM 后端）。

**规模**：10 个包 / 32 个 `.cj` 文件（27 个实现 + 5 个测试文件，33 个用例）。

| 包 | 文件 | 职责 |
| --- | --- | --- |
| `winun`（root） | `main.cj` | 入口：经 Win32 取命令行 → 交给 CLI |

| `winun.app` | `host.cj` | 宿主：装配平台实现、注册热键、消息循环、配置热重载 |
| `winun.core` | `registry.cj`、`session.cj`、`dispatcher.cj` | 窗口/应用/组索引；组状态与焦点记忆；动作执行（启动集合、组切换、布局应用、贴边、最大化/还原） |
| `winun.domain` | `model.cj`、`chord.cj`、`action.cj`、`matcher.cj` | 窗口与组模型、布局声明、组合键解析（含 VK 映射表）、动作字符串解析、窗口识别规则 |

| `winun.config` | `schema.cj`、`loader.cj` | JSON → `ConfigSnapshot`：类型校验、未知键策略、交叉引用校验、错误码 |
| `winun.platform` | `backend.cj` | 平台抽象 trait（WindowBackend / AppLauncher / HotkeyBackend / Clock）+ Null 实现 |
| `winun.win32` | `ffi.cj`、`handle.cj`、`backend.cj`、`pump.cj`、`cmdline.cj` | Win32 FFI 声明、句柄表、窗口枚举/操作/启动实现、消息循环封装、命令行读取 |
| `winun.infra` | `json.cj`、`text.cj`、`log.cj`、`errors.cj`、`files.cj` | 自研 JSON 解析器与序列化、UTF-8↔UTF-16、`%VAR%` 与 `${env:VAR}` 展开、日志、错误类型、文件工具 |

## 4. 遇到的问题与解决方案

共记录 36 个问题，分四类（P 平台 7 条、L 语言 17 条、D 设计 9 条、W 流程 3 条）。每条给出「现象 → 根因 → 解决 → 固化位置」。

### 4.1 平台与环境类（P）

| 编号 | 现象 | 根因 | 解决方案 | 固化位置 |
| --- | --- | --- | --- | --- |
| P-01 | `cjc` / `cjpm` 提示「无法识别为 cmdlet」 | SDK 装了但没进 PATH | 每条命令前 dot-source `envsetup.ps1` | README 快速开始 |
| P-02 | 某次运行报退出码 `-1073741515`（`STATUS_DLL_NOT_FOUND`）且无任何输出 | 该次 shell 里 envsetup 未生效，运行时 DLL 目录不在 PATH | 显式设置 `$env:CANGJIE_HOME` 与 `$env:PATH`（`bin`、`tools\bin`、`lib\windows_x86_64_cjnative`、`runtime\lib\windows_x86_64_cjnative`），不依赖脚本副作用 | spike-report §2.4 |
| P-03 | 链接报 `ld.lld: error: failed to write the output file: Permission denied` | 上一轮启动的 `main.exe` 仍在运行，占用产物文件 | `Get-Process main \| Stop-Process -Force`；若被沙箱拒绝（`taskkill` 返回 Access denied）则改用作业取消终止 | 本文件 §7 提示 |
| P-04 | `main(args: Array<String>)` 只要访问 `args` 就永久挂起（连 `args.size` 都不返回） | 仓颉运行时在本机环境下取进程参数的行为异常 | 入口改 `main()`，命令行用 Win32 自取（见 §4.5） | `src/win32/cmdline.cj` + spike-report §2.1 |
| P-05 | `SetLastError(1234)` 后立刻 `GetLastError()` 得到 0；失败的 `LoadLibraryW` 之后同样是 0 | 本环境（沙箱/运行时）下 Win32 最后错误码不可用 | 错误诊断以「返回值 + API 名」为准；需要结构化错误码时再引入 C shim（见 §4.6） | `win32` 各调用点注释 + spike-report §2.2 |
| P-06 | `RegisterHotKey` / `SetWindowPos` / `MoveWindow` 返回 FALSE 且错误码为 0 | 跨进程窗口句柄被沙箱拦截；而热键失败实为**组合键已被占用**（结论已修正，见 §4.7） | 自建窗口可正常操作 → 用 `selftest` 在沙箱内真实验证；仅跨进程部分留人工会话 | selftest + spike-report §2.3 |
| P-07 | 把输出重定向到文件再读，中文变成乱码（如「仓颉」→「浠撻」） | 程序输出 UTF-8，PowerShell 默认按 GBK 解码重定向文件 | 直接管道输出正常；如需重定向，读取时显式指定 UTF-8 | 待办：启动时调用 `SetConsoleOutputCP(65001)` |

### 4.2 仓颉语言 / 编译器类（L）

| 编号 | 现象 | 根因 | 解决方案 |
| --- | --- | --- | --- |
| L-01 | `expected Int32, found Int64` | 整型字面量默认 `Int64` | FFI 形参处显式标注：`let id: Int32 = 1` |
| L-02 | `expected Int64, found Int32`（数组下标） | 数组下标必须是 `Int64` | `for (i in 0..Int64(n))` |
| L-03 | 元组 `.0` 解析报错 | 仓颉元组用下标访问 | 写 `pair[0]` |
| L-04 | `CPointer<UInt16>(buf)` 编译失败 | 构造函数只接受 `CPointer`/`CFunc` | `acquireArrayRawData(arr)` → 取 `handle.pointer` → 用后 `releaseArrayRawData(handle)`，且全程在 `unsafe` 内 |
| L-05 | `LibC.malloc<T>(16)` 报「缺少具名前缀 count:」 | 该 API 的计数参数是具名参数 | `LibC.malloc<T>(count: 16)` |
| L-06 | 无法把整数还原成 `CPointer` | `CPointer` 只有 `toUIntNative()` 单向转换 | `win32` 维护 id ↔ HWND 句柄表（`registerHandle` / `toHwnd`） |
| L-07 | `HashMap<CPointer<Unit>, Int64>` 泛型约束不满足 | `CPointer` 不满足 `HashMap` 的键约束 | 以 `Int64`（地址）为键 |
| L-08 | `foreign` 与 `public` 修饰符冲突（36 处） | 语言规定二者不可共存 | 去掉 `public`；包外需要时写公开包装函数（`win32/pump.cj`、`cmdline.cj`） |
| L-09 | `invalid binary operator == on Enum` | 简单枚举未派生相等比较 | 用 `match` 分支代替 `==` |
| L-10 | `const TOP_KEYS = [...]` 报「数组不是常量」 | `const` 只接受编译期常量 | 改 `let`（或用 `VArray`） |
| L-11 | `File.appendTo(path, line + "\r\n")` 类型不符 | 第二个参数是 `Array<UInt8>` | 传 `(line + "\r\n").toArray()` |
| L-12 | 测试里用多行字符串写 JSON 反而解析失败 | `"""..."""` 多行字符串会处理转义（`\\` → `\`） | 测试中用 `String.fromUtf8([0x5C])` 构造反斜杠，避开多层转义 |
| L-13 | 父类型列表写 `winun.platform.Clock` 报「未声明的类型名」 | 全限定名不能直接用于父类型列表 | 先 `import winun.platform.*` 再写 `Clock` |
| L-14 | `undeclared identifier ArrayList` / `Int64.parse` | 缺少 `std.collection.*` / `std.convert.*` | 补 import（`Int64.parse` 属于 `std.convert` 扩展） |
| L-15 | `@Assert(cond, "消息")` 编译失败 | 该宏把第二个参数当作期望值比较 | 只用单参数断言；调试信息改用打印或断言范围 |
| L-16 | 测试访问 `map["missing"]` 抛异常 | `HashMap` 下标在键不存在时抛异常 | 用 `map.get(k)` 返回 `Option` 再 match |
| L-17 | `v[i] = Int32(n)` 报「无法给下标表达式赋值」（当 `v` 是 `Array<Int64>` 时） | 元素赋值要求类型严格一致 | 用若干标量变量代替数组，或在构造时就确定元素类型 |

### 4.3 设计与逻辑类（D）

| 编号 | 现象 | 根因 | 解决方案 |
| --- | --- | --- | --- |
| D-01 | `main.exe validate` 卡死不见输出，`version` 也一样 | CLI 参数判定写反：已知命令被当成位置参数，`command` 保持默认值 `run`，于是进了常驻消息循环 | 修正判定为「首个位置参数若是已知命令才作为命令」；这条伪装成「程序挂起」，是本次排查耗时最长的问题 |

| D-03 | 文档承诺仓库随附 `config/winun.json` 与 `winun.schema.json`，但工作区没有 | 文档与实现进度不同步 | 补齐两个文件，并让 `validate` 直接吃这份示例（构建与文档互相印证） |
| D-04 | `spike/` 下遗留探针文件与临时输出 | 验证阶段留下的临时产物 | 清理并加入 `.gitignore`（`target/`、`*.exe`、`o_*.txt` 等） |
| D-05 | **用户实测：按 `win+alt+q` 无任何反应** | 消息泵包装函数 `getMessage(msg: MSG)` 把结构体**按值**传入，`GetMessageW` 写入的是函数内的副本，调用者的 `msg` 始终是全 0 → `WM_HOTKEY` 分支永不命中，进程只是安静地阻塞在消息循环上 | 改为 `pumpMessage()` 返回携带 `MSG` 的结果对象；并把"注册 → 自投递 WM_HOTKEY → 消息循环取回"加入 `selftest` 作为回归用例 |
| D-06 | 热键注册部分失败后，退出/重载时注销会漏 | 注销按"成功数量"顺序遍历 id（1..count），而失败的注册会让 id 出现空洞 | `Win32Hotkeys` 记录**真正注册成功**的 id 列表，按列表注销 |
| D-08 | `list windows` 输出中途崩溃：`Invalid utf8 byte sequence` | 三处 UTF-8 边界问题：① 窗口标题按字节硬截断（`s[0..28]`）会切断多字节字符；② `expandEnv` 逐字节 `String.fromUtf8([b])` 在中文上必然构造非法 UTF-8；③ 标题里的孤立代理项（`0xD800`/`0xDC00`）被原样编码 | ① 新增 `truncateUtf8`：按字节上限截断并回退到字符边界；② `expandEnv` 改为按字节累积、末尾一次性 `fromUtf8`；③ `utf16Decode` 把孤立代理替换为 U+FFFD；三条都补了单测 |
| D-09 | 窗口清单混入大量无法管理的系统窗口（`Shell_TrayWnd`、`DummyDWMListenerWindow`、`Progman`…） | 枚举只判了"可见"，没有排除外壳/工具窗口 | 新增候选判定：可见 + 有非空标题 + 非 `WS_EX_TOOLWINDOW`（除非同时有 `WS_EX_APPWINDOW`）+ 类名黑名单；清单从 14 条噪声降到 4 条真实应用窗口 |
| D-07 | 日志每写一行都刷一次"无法写入日志文件…路径不存在"；修好目录后日志文件仍然不生成 | ① 日志目录不存在时写文件必然失败且每次都重复提示；② `Directory.create` 对已存在目录的行为不稳定，预判式建目录会把 `fileWritable` 误置为 false，导致静默丢失全部日志 | 改为**惰性策略**：首次追加失败 → 尝试建目录（忽略异常）→ 再追加一次 → 仍失败才降级为"仅控制台"并只提示一次；不再预判目录状态 |

### 4.5 重点问题一：`main(args)` 挂起

**现象**：`main(args: Array<String>)` 中任何对 `args` 的访问都会让进程永久阻塞、且不产生任何输出；同一个二进制换成 `main()` 立即正常。第一次遇到时被误判为「JSON 解析死循环」，实际连第一行 `println` 都没执行。

**解决方案**：入口改为无参 `main()`，命令行自行获取：

```cangjie
main(): Int64 {
    let args = commandLineArgs()   // GetCommandLineW + WideCharToMultiByte(CP_UTF8)
    return runCli(args)
}
```

- `win32/cmdline.cj` 提供 `readUtf16Pointer`（UTF-16 指针 → UTF-8 字符串）、`splitWindowsCommandLine`（按 Windows 规则处理引号）、`commandLineArgs`。
- 拆分函数是纯函数，已纳入单测；同时也让路径含空格的 `--config "C:\a b\winun.json"` 可用。

### 4.6 重点问题二：`GetLastError` 不可用

**现象**：`SetLastError(1234)` 后立即 `GetLastError()` 返回 0；`LoadLibraryW("no-such-lib.dll")` 正确返回 NULL，但随后错误码仍是 0。说明调用本身到达了系统 DLL（NULL 返回值正确），只有错误码通道失效。

**解决方案**：把「错误码」降级为可选信息，主判据只信返回值：

| 层次 | 做法 |
| --- | --- |
| 调用点 | `Bool`/指针返回值判定成败，失败时记录 `API 名 + 参数摘要` |
| 日志 | `Win32Error(api, code, message)` 结构保留 `code` 字段，为 0 时标注「错误码不可用」 |
| 后续 | M3 若确需精确错误码，在 `native/` 下加 C shim（`[ffi.c]` 挂载），由 C 侧一次性取回错误码与消息 |

### 4.7 重点问题三：沙箱到底限制了什么（结论已修正）

第一次探测时得到"热键与窗口写操作全部被拦截"的结论，**后续实验证明这个结论一半是错的**，这里给出修正后的实测事实。

| 能力 | 实测结果 | 说明 |
| --- | --- | --- |
| 枚举/读取窗口（`EnumWindows`、`GetWindowRect`、`IsWindow`、`GetWindowTextW`、`GetForegroundWindow`） | 可用 | 一次枚举到 977 个顶层窗口、30 个可见 |
| 创建自己的窗口（`RegisterClassExW` + `CreateWindowExW`） | 可用 | 沙箱内成功创建隐藏窗口，`sizeOf<WNDCLASSEXW>() == 80` |
| 操作**自己进程**的窗口（`SetWindowPos` / `ShowWindow`） | 可用 | 位置从 `(50,60,450,360)` 改到 `(200,220,900,720)`，读回校验一致 |
| 操作**其它进程**的窗口（前台窗口、记事本窗口） | 被拦截 | 返回 FALSE；这是沙箱真正限制的部分（跨进程 USER 句柄） |
| 注册全局热键 `RegisterHotKey` | **可用** | `win+alt+q` / `win+alt+f11` / `win+alt+f12` / `ctrl+alt+f11` 均注册成功并正常注销 |
| `GetLastError` 错误码 | 不可用 | 恒为 0，所以"注册失败"无法区分是被占用还是被限制 |

**为什么第一次结论错了**：第一次只试了 `win+alt+1`，而本机上该组合键（以及 `win+alt+2`、`win+alt+3`、`win+alt+tab`）确实已被其它程序占用；错误码又恒为 0，于是被误判成"沙箱禁止注册热键"。修正后逐个试探多个组合键才看清真相。

**顺带发现并修复的真实缺陷**：`ShowWindow` 的返回值是"调用**前**是否可见"，不是"是否成功"。原先 `Win32WindowBackend.show/hide/minimize/maximize/restore` 直接把该返回值当成功标志，导致隐藏窗口执行 `show()` 时误报失败（`selftest` 第一次运行就抓到了这一条）。现已改为以调用后的 `IsWindowVisible` / `IsIconic` / `IsZoomed` 实际状态为准。

### 4.8 解决方案：把"沙箱限制"降级成"分层验证"

针对不同层级采用不同手段，让绝大部分能力**在当前沙箱内就能被真实验证**，只有真正需要跨进程的部分才依赖人工会话。

| 层级 | 手段 | 覆盖范围 | 是否受沙箱影响 |
| --- | --- | --- | --- |
| T1 平台自检 | `winun selftest`：ABI 断言 + **自建隐藏窗口**跑真实 `solve → SetWindowPos → 读回校验` + `ShowWindow` 状态往返 + 热键注册探测 + 显示器工作区 | 平台写路径（除跨进程） | 不受影响，16/16 通过 |
| T2 编排单测 | `RecordingWindowBackend` / `RecordingLauncher` / `RecordingHotkeys` / `FakeClock`：把平台调用录下来做断言 | 启动集合、组切换、`onSwitchAway`、布局应用、贴边、重载/退出标志 | 不受影响，33 个用例全绿 |
| T3 纯逻辑单测 | JSON、UTF-16、组合键、动作、布局解算、配置校验 | 全部领域逻辑 | 不受影响 |
| T4 人工会话验收 | 在普通 PowerShell / 双击运行 `winun run`，操作真实应用窗口 | 跨进程窗口操作、真实按键触发 WM_HOTKEY | 需要 |

**关键设计**：T1 之所以可行，是因为沙箱拦的是"**其它进程**的窗口句柄"，而不是窗口功能本身。于是让 winun 自己创建隐藏探针窗口，就能用**真实的 Win32 调用链**（真实 `SetWindowPos`、真实 `GetWindowRect`）验证布局执行路径，而不是用假对象糊过去。

**T4 具体怎么做**（三步，约两分钟）：

```powershell
# 1) 普通 PowerShell（不要用受限沙箱），先自检
. "C:\Program Files (x86)\Cangjie\envsetup.ps1"
.\target\release\bin\main.exe selftest

# 2) 常驻运行并观察日志
.\target\release\bin\main.exe run --config config\winun.json --console

# 3) 另开一个窗口，按热键（先用 config 里没被占用的组合键，或改成 win+alt+f11 之类）
#    期望：日志出现"执行动作：launch dev-env"，随后应用被拉起并按布局摆放
```

若确实需要**由代理在会话内驱动跨进程验证**，可对单条命令申请一次性放宽沙箱（`sandbox_permissions`，需要人工批准）；但通常没有必要——把 T1/T2/T3 做扎实，人工只需确认 T4 这一小段。

### 4.9 实测反馈驱动的修复（第一轮真机试用）

用户在普通 PowerShell 里按 README 跑通了前四步（构建、自检、校验、列窗口），但第 5 步 `run` 出现"热键注册成功却按键无反应"。这次真机试用暴露了单元测试覆盖不到的接线问题：

| 环节 | 内容 |
| --- | --- |
| 现象 | `win+alt+q` 无反应；日志里该热键显示"已注册"；另有每行一次的日志目录警告 |
| 定位 | 消息泵 `getMessage(msg: MSG)` 按值传参，`GetMessageW` 的回写只落在副本上；宿主循环读到的 `msg.message` 恒为 0 |
| 修复 | `pumpMessage()` 用结果对象带回 `MSG`；顺带修掉热键注销的 id 空洞与日志目录缺失 |
| 回归 | `selftest` 新增"注册 → 自投递 `WM_HOTKEY` → 消息循环取回"检查（不需要真实按键），自检项从 16 升到 17 |
| 顺带发现 | 本机 `win+alt+1/2/3/tab/shift+tab/w/r/方向键` 已被其它程序占用；另外**上一轮未退出的 winun 进程会独占已注册的热键，并锁住 `main.exe` 导致重新编译报 `ld.lld: Permission denied`**。示例配置改用实测空闲的 `win+alt+f1..f12 / q / e / z`，并新增 `winun selftest --config` 逐条探测配置里的组合键 |

**完整链路验证（修复后在正在运行的进程上实测）**：用一个"冒烟配置"（`config/winun.smoketest.json`，只绑定 `win+alt+f1 = config reload`、`win+alt+z = quit`）启动 winun，再向它的消息队列投递操作系统在热键按下时投递的同一种消息（`WM_HOTKEY`），日志逐条吻合：

```text
[INFO ] [host] winun 已启动，等待热键（线程 284076）
[DEBUG] [host] 收到热键消息 id=1
[DEBUG] [dispatcher] 执行动作：config reload
[INFO ] [config] 配置已热重载：apps=0 launches=0 layouts=0 groups=0 hotkeys=2
[DEBUG] [host] 收到热键消息 id=2
[DEBUG] [dispatcher] 执行动作：quit
[INFO ] [host] 收到退出动作，准备结束
```

进程以退出码 0 正常结束。这条链路覆盖了"消息 → 循环 → 动作分发 → 执行 → 优雅退出"，唯一未在会话内覆盖的只剩"物理按键触发"这一跳（沙箱禁止输入注入，需人工按键确认）。

**经验**：跨 FFI 边界的**结构体出参**是本项目最容易出错的一类代码——C 侧写内存、仓颉侧按值传参，编译器不会报错，运行时也不崩溃，只是"静默不生效"。因此凡是"Windows 回写结构体"的 API，一律用结果对象返回，并配一个不依赖人工操作的闭环自检。

### 4.10 真机配置落地（应用路径与匹配规则）

按用户要求把配置从"示例路径"改成**本机实际安装路径**，方法固定为三步，换机器可复用：

| 步骤 | 手段 | 本机结果 |
| --- | --- | --- |
| 1 查注册表 App Paths | `HKLM/HKCU\...\App Paths` 下的 `(default)` | 拿到 `code.exe → D:\Microsoft VS Code\Code.exe`、`firefox.exe → D:\Firefox Nightly\firefox.exe`、`msedge.exe`、`wps.exe` 等权威路径 |
| 2 查 PATH | `Get-Command code,wt,chrome,...` | `code`、`wt`、`notepad` 可用；本机没有 Chrome，改用已装的 Edge |
| 3 查运行中进程 | `Get-Process | Where-Object { $_.Path }` | 交叉验证 exe 名，确保 `match.exe` 与实际窗口进程一致 |

配置落地结果：8 个应用（vscode / terminal / firefox / edge / wps / explorer / notepad / music）、4 个启动集合、5 个布局、3 个组、15 个热键。

**匹配规则必须用真实窗口验证**：为此给 `list windows` 增加了「匹配应用」列，实测输出（当时正在运行 Edge）：

```text
0x67588   286404   msedge.exe            Chrome_WidgetWin_1      新建标签页 和另外 1     edge
0x131486  302036   DeepSeek Harness.exe  Chrome_WidgetWin_1      winun 窗口管理项目初    -
...
其中 1 个窗口匹配到配置中的应用（这些窗口会被收编与布局）
```

注意：Electron 系应用（VS Code、DeepSeek Harness）类名同为 `Chrome_WidgetWin_1`，所以**不能只靠类名**区分，必须配合 `match.exe`（VS Code 还额外加了标题正则）。

## 5. 本步形成的工程约定

| 约定 | 说明 |
| --- | --- |
| FFI 只出现在 `winun.win32` | 其它包不得出现 `unsafe`、`CPointer`、`CString`；对外只暴露领域类型 |
| 句柄不进入领域层 | `WindowId` 是不透明 `Int64`，HWND 由 `win32` 的句柄表保管 |
| 领域层无平台类型 | 平台差异收敛在 `winun.platform` 的 trait 之后，测试可注入 `Null*` 实现 |
| 纯函数优先 | 布局解算、键位/动作解析、配置映射、JSON 解析都是纯函数，可单测、可 dry-run |
| 错误码分段 | `E1xxx` JSON 语法（带 `file:line:col`）、`E2xxx` 语义、`E3xxx` 运行时；退出码 0/2/3/4/5 |
| 测试文件命名 | `*_test.cj`，与被测包同目录，`cjpm test` 执行 |
| 配置键名 | JSON 用 camelCase；id 与动作名用 kebab-case |
